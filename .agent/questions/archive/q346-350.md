## Question 348: Page 01 Branch Visual Language

Status: provisionally self-answered; user override remains open

Provisional selection: 1

Why it matters: `Direct` and `Explore` already have different authored
geometry, but Page 01 still needs a non-color visual language that previews the
difference without making either branch look unsafe, more valuable, or governed
by a different platformer.

Question: How should Page 01 distinguish `Direct` and `Explore` before and during play?

1. Keep both branches on the same sepia conservation paper and shared safe-edge
   grammar. Mark `Direct` with one bold continuous ink route, circular node
   stamps, and two broad crease spans. Mark `Explore` with a paired stitched
   route, diamond node stamps, one extra folded span, a stitched-bookmark
   checkpoint, and an optional margin-clue curl. Carry the selected branch's
   small route mark onto its folded supports without replacing any platform,
   hazard, checkpoint, or goal cue. Use explicit labels, topology preview, and
   an equivalent ordered route list; color accents remain supplemental.
2. Give `Direct` a blue line and `Explore` a red line, but otherwise use the
   same shapes, textures, labels, topology display, and descriptions so color
   is the only reliable distinction.
3. Render both branches with identical paths, node marks, fold silhouettes,
   checkpoint presentation, and previews, revealing their actual difference
   only after JR is already running.
4. Give each branch an unrelated material family, control scheme, platform
   grammar, difficulty tier, reward value, and goal form so they behave like
   separate mini-games rather than two routes through one authored graph.

## Question 349: Page 01 Cabinet State Sequence

Status: provisionally self-answered; user override remains open

Provisional selection: 1

Why it matters: the current Page 01 presentation has only a generic map-unfold

the visible mesh decide progress.

Question: How should the Page 01 cabinet visibly progress from placement through revisit?

1. Use one bounded domain-driven sequence. `Dormant` keeps the dark-wood doors
   latched around a visible paper tab; `Inviting` releases one brass latch and
   labels `Open Map`; `Active` opens both doors onto the flat labeled branches;

   route remains a pressed labeled outline; `Checkpoint` fills the durable
   stitched bookmark; `Goal-ready` aligns and opens the map-heart seal; and
   `Complete/Revisit` settles half-open around the embossed chosen route,
   closed heart seal, owned fragment receipt notch, and available replay
   branch. Each transition acknowledges persisted semantic state through
   bounded motion or an equivalent static, reduced-motion, silent, descriptive,
   and non-spatial form.
2. Play one long automatic cabinet-opening cinematic after placement, hide all
   route and state information until it ends, and let the animation timeline
   decide when planning, running, saving, completion, and reward begin.
3. Keep the cabinet, paper, route marks, bookmark, goal, and receipt visually
   identical from dormant placement through completion, communicating every
   state only through a separate text HUD.
4. Randomly rearrange doors, drawers, paper layers, pins, lighting, and route
   folds on every launch, using procedural physics and whichever animation
